## [Unreleased]

### Fixed
- **Sentinel open-marker no longer prefix-matches sibling block names ([#12](https://github.com/erbiker/jtr/issues/12)).** `managed::open_marker(name)` returned `# >>> jtr:{name}` with no boundary character, so `starts_with` checks in `managed::remove` and `extract_block_text` (the new `jtr diff` helper) also matched recipes whose names started with `name`. Installing `foo-bar` and then `foo` would silently strip `foo-bar`'s entire managed region during the `upsert → remove` step of installing `foo` — `upsert`'s round-trip sanity check counts the *target* block, not bystanders, so the corruption was undetected. The fix appends `@` to the returned marker (matching the rendered `# >>> jtr:<name>@<version> >>>` boundary in the open line), which makes both `starts_with` call sites correct without further changes. `parse_all` was already correct because it routes through `parse_open`, which requires the `@`-delimited version suffix. Two regression tests: a unit test in `src/managed.rs` exercises `remove` directly against an overlapping-prefix document, and an integration test in `tests/cli.rs` replicates the issue's repro (`install foo-bar; install foo; remove foo`) and asserts `foo-bar` survives. The bug was latent — no recipe pair in the wild has overlapping prefixes — but the blast radius would have grown once tap recipes proliferate.

### Added
- **`jtr show` + `jtr diff` for audit-before-write.** `jtr show <name>` prints the rendered managed block that `install` *would* write — the same sentinel header, source/pinned/depends-on lines, and target snippet — to stdout without touching the project file. Resolves through the existing `Sources::find_at` path, so curated names, tap-qualified names (`user/repo/recipe`), and `@version` pins all work. Especially useful for inspecting a community-tap recipe before letting it land. `jtr diff <name>` runs the same render and produces a unified diff against the currently-installed block (using the `similar` crate); exit 0 means the on-disk block matches what `install` would write right now, exit 1 means it doesn't — a drop-in CI check for "are my recipes current." A diff of an uninstalled recipe renders the whole block as additions. Pinned blocks compare against the *pinned* version, not latest — pinning is a deliberate freeze, so drift against latest is `doctor`'s job, not `diff`'s; `diff <name>@<latest>` is the escape hatch when you want to see what an unpin would actually change. The exit-code path uses `std::process::exit(1)` rather than `bail!` so the user sees a clean diff without anyhow's `Error:` prefix, matching `git diff`. Both commands honour the global `--no-cache` flag and trip the same "tap not configured" diagnostic as install when a `user/repo/recipe` name references a missing tap. Adds `similar = "3"` (MIT, passes `cargo deny check`); `split_pin` and `describe_missing` in `commands/install.rs` are now `pub(crate)` so the new commands share the install resolution surface rather than duplicating it.
- **Local disk cache for index and manifest fetches.** Every `jtr search`/`install`/`update`/`doctor` now persists what it fetches under the platform cache dir (`~/Library/Caches/dev.jtr.jtr/` on macOS, `~/.cache/jtr/` on Linux honouring `XDG_CACHE_HOME`); `JTR_CACHE_DIR` overrides for tests and sandboxing. `index.json` bodies are keyed by URL with a one-hour TTL per DEEP_DIVE §3; manifests are content-addressed by their declared SHA-256, so they're immutable — a rotated checksum in the parent index just points lookups at a different filename. Each tap's index is cached independently by URL so one stale tap doesn't bust the others. Cache writes are atomic (tempfile + rename within the same directory so the persist is a true atomic rename, not a cross-filesystem fallback) and best-effort: a full disk or read-only fs emits a yellow `warning:` and the command keeps going. Reads defensively re-verify the manifest hash before serving cached bytes — a corrupted cache file is detected and silently removed rather than returned to the caller. `--no-cache` (global flag) bypasses both read and write for one invocation; `file://` URLs are never cached (test isolation, no benefit anyway). The HTTP fetch path is unchanged when caching is bypassed or unavailable; the cache module (`src/cache.rs`) is a strict overlay. Adds `tempfile = "3"` to runtime deps (was dev-only) for the atomic-write tempfile helper.
- **Version pinning at install (`jtr install <name>@<version>`).** Users can pin a recipe to a specific published version for reproducible setups; bare `jtr install <name>` continues to track the latest. The recipe-name parser splits on the rightmost `@`, so tap-qualified names work too (`jtr install user/repo/recipe@1.2.0`). Errors are concrete: an empty version (`foo@`) tells the user to drop the `@` or supply a version; a pin that isn't published lists every available version from the index. The on-disk managed block records the pin inline as `# pinned: <version>`. `jtr update <name>` now respects pins — it skips them by default with a message that names the pin and offers `jtr update <name> --unpin` (bump to latest, drop the pin) or `jtr install <name>` (bare install also overwrites the pin) as documented escape hatches. `jtr doctor` distinguishes pinned-and-current (`✓ pinned, up to date`, no drift warning) from pinned-but-no-longer-published (`✗` with the available list). Transitive dependencies stay free per the v1 design — pinning A doesn't pin its deps; a full lockfile is deferred until users ask. The index schema extends `IndexEntry` with an optional `versions: [...]` array enumerating every published version's `manifest_url`/`sha256`; absent the array (older or single-version indices), the top-level `version` is the only installable one and the available list still renders cleanly.
- **Recipe dependencies.** Recipe manifests can declare a `dependencies: ["name", "user/repo/name"]` array; `jtr install` resolves transitively and installs every dep before the dependent, preserving topological order in the project file. Bare dep names resolve to the curated index, `user/repo/recipe` names resolve to a configured tap. Diamond dependencies install each shared leaf exactly once; cycles (including self-loops) abort with the offending chain (`a → b → a`) before anything is written; dep references to an unconfigured tap point the user at `jtr tap add <tap>`. The on-disk managed block records the dep list inline as `# depends-on: a, b`, which lets `jtr remove` compute reverse-deps without hitting the network: removing a recipe that others depend on now errors with the dependent list and a `--force` hint (`jtr remove <name> --force` overrides). `update` was updated in lock-step so re-fetching a recipe rewrites its `# depends-on:` header if the manifest's dep list changed.
- **`jtr tap` for decentralized publishing.** New top-level subcommand modelled on Homebrew taps. `jtr tap add <user/repo>` adds a community-maintained index (defaulting to `https://raw.githubusercontent.com/<user/repo>/main/index.json`, with a `--url` override for self-hosted or `file://` indices); `jtr tap list` / `jtr tap remove` round it out. Taps are persisted as `taps.toml` under the platform config dir (`~/.config/jtr/` on Linux, `~/Library/Application Support/dev.jtr.jtr/` on macOS via the `directories` crate), or wherever `JTR_CONFIG_DIR` points if set. `jtr search` aggregates curated + every reachable tap, prefixing tap recipes with their tap name and listing the source as a separate column. `jtr install user/repo/recipe-name` routes through the named tap; the on-disk managed block is also written under the full `user/repo/recipe-name` identifier, so a tap recipe and a curated recipe of the same name coexist without collision. `update`, `doctor`, `list`, and `remove` all treat tap blocks as first-class — they were updated in lock-step to look recipes up through the multi-source aggregator (`src/sources.rs`) rather than only the curated index. Unreachable taps are skipped with a warning instead of failing the whole command, so one broken tap doesn't brick `jtr search`. New deps: `directories = "5"` (re-added) and `toml = "0.8"`.
- **Release infrastructure.** New [`.github/workflows/release.yml`](.github/workflows/release.yml) triggered on `v*` tag pushes builds release binaries for Linux x86_64, macOS arm64, macOS x86_64, and Windows x86_64, computes a `SHA256SUMS` file, and attaches everything to a GitHub release. `cargo publish --dry-run --locked` runs as a gating step (also added to the regular `quality` CI job so packaging breakage surfaces on every PR). The actual `cargo publish` to crates.io remains a manual step from the maintainer's machine — pre-alpha + crates.io irreversibility makes auto-publish-on-tag a footgun. Procedure documented in [CONTRIBUTING.md → Cutting a release](CONTRIBUTING.md#cutting-a-release).
- **Trimmed crate tarball.** `Cargo.toml` gained a [`package.exclude`](Cargo.toml) list that keeps dev-only files (`.github/`, `jtr-index/`, `scripts/`, `tests/`, `deny.toml`, `justfile`, CoC/SECURITY/TESTING/CONTRIBUTING markdown) out of the published crate. `cargo package --list` drops from 44 files to 23 — just `src/`, `README.md`, dual licenses, `CHANGELOG.md`, and the Cargo files.

## [0.1.0] — 2026-05-23

First tagged release. Pre-alpha — APIs and recipe formats will change.

### Added
- **`jtr install <name>`** — fetches a recipe manifest from the registry index and writes a sentinel-delimited managed block into the project's `justfile`.
- **`jtr remove <name>`** — strips a previously-installed managed block, collapsing surrounding blank lines so the file stays tidy across install/remove cycles.
- **`jtr update [<name>]`** — re-fetch one or all installed recipes and replace their managed block when the registry has a newer version. Reports `updated X → Y` for version bumps, `refreshed @X` when the block had drifted from canonical, and `already at version X` when nothing changed. Wires through to the existing `Registry` and `managed::upsert` pipeline so the same atomicity/idempotency guarantees apply.
- **`jtr list`** (alias `jtr ls`) — lists the names and versions of all jtr-managed recipes in the current project file.
- **`jtr search [query]`** — case-insensitive substring search across recipe names and descriptions in the registry index.
- **`jtr init [--target task]`** — scaffolds a minimal `justfile` (default) or `Taskfile.yml` in the current directory with a `default:` recipe that lists every other task. Refuses to overwrite any existing `justfile` / `Justfile` / `.justfile` (or any case variant of `Taskfile.yml`) so it's safe to run in a directory you're not sure about. Closes the activation-energy gap for brand-new projects — `jtr install <recipe>` works immediately after.
- **`jtr doctor`** — diagnose every installed recipe in one shot. Reports orphaned managed blocks (recipe no longer in the registry, with a `jtr remove` hint), version drift (newer manifest available, with the new version highlighted), and missing tools (anything from the manifest's `shells_out_to` that isn't found on `PATH`). Exits non-zero if any problem is found, so it's drop-in for CI. PATH lookup is implemented with a tiny stdlib helper (`std::env::split_paths` + Unix executable-bit check) — no new runtime deps.
- **Checksum verification on fetch.** `IndexEntry` gains an optional `sha256` field; `Registry::load_manifest` now hashes the fetched manifest bytes and refuses to return a manifest whose hash doesn't match what the index declared. Errors include both the expected and actual hashes plus the source URL. If an index entry omits `sha256`, install/update succeeds with a `warning:` printed to stderr — backwards-compatible during the v1 rollout but visible enough that maintainers notice and add the hash. All 5 seed recipes in `jtr-index/index.json` ship with checksums.
- `scripts/recompute-checksums.sh` (also wired up as `just rehash`) — Python-only, no external deps. Walks `jtr-index/index.json`, recomputes the SHA-256 of every referenced manifest, and rewrites the file in place. Idempotent: a no-op run produces a zero-line diff.
- **Registry index loader** supporting `https://`, `http://`, `file://`, and bare local-path URLs (configurable via `--index` or `JTR_INDEX_URL`).
- **Auto-detection** of `justfile` / `Justfile` / `Taskfile.yml` / `Taskfile.yaml` in the current directory; `--file` override.
- **`task` (YAML) target stub** — install detects `Taskfile.yml` and exits with a friendly "not yet implemented" message including the would-be snippet. Full YAML write support deferred.
- **Bundled sample registry** under `jtr-index/` with 5 seed recipes: `postgres-dev`, `redis-dev`, `rust-lint-format`, `node-lint-format`, `clean`. All recipes use language prefixes (`rust-lint`, `node-lint`, etc.) so installing multiple language formatters together doesn't collide.
- **Quality tooling: `cargo-deny` + `cargo-machete` + `taplo`.** Three pieces of supply-chain and formatting hygiene, wired into `just check` and a `quality` CI job (runs once on Ubuntu via `taiki-e/install-action`, no per-OS duplication). `cargo-deny check` enforces a permissive-license allowlist on every transitive dep, fails on RustSec advisories or yanked crates, and denies git/unknown-registry sources; config is in [`deny.toml`](deny.toml) (~50 lines, dev-deps excluded). `cargo-machete` flags unused dependencies on every PR. `taplo fmt --check` keeps `Cargo.toml` and `deny.toml` consistently formatted. Trade-off documented in [CONTRIBUTING.md](CONTRIBUTING.md): `just check` now needs network for the advisory-DB fetch; everything else still runs offline.
- **CI** — GitHub Actions workflow at [.github/workflows/ci.yml](.github/workflows/ci.yml) running fmt + clippy + tests + smoke + validate-index on Linux and macOS, plus a separate `quality` job (deny + machete + taplo).
- **Tests** — unit suite for `managed.rs` (render, parse, upsert, remove, validate-name); 25 end-to-end integration tests in [`tests/cli.rs`](tests/cli.rs) using `assert_cmd`; HTTP integration test in [`tests/http.rs`](tests/http.rs) that stands up `tiny_http` on an ephemeral localhost port, serves the bundled `jtr-index/` verbatim, and exercises the production HTTP fetch path (every other test uses `file://`).
- **Project `justfile`** with `just check` (fmt + clippy + taplo + machete + deny + test), `just smoke` (end-to-end install/list/remove loop), and `just validate-index` (every seed recipe parses as valid `just` syntax).
- **Open-source repository hardening:**
  - Dual [MIT](LICENSE-MIT) / [Apache-2.0](LICENSE-APACHE) license files (matching the `Cargo.toml` declaration and the Rust ecosystem convention).
  - [CONTRIBUTING.md](CONTRIBUTING.md) — development setup, PR workflow, and recipe-authoring guide.
  - [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) — based on Contributor Covenant v2.1.
  - [SECURITY.md](SECURITY.md) — private vulnerability-disclosure process.
  - GitHub issue templates (bug, feature, recipe proposal) and a pull request template under `.github/`.
- [README.md](README.md) — user-facing intro.
